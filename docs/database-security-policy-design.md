# Database Security Policy（DSP）導入設計

状態: 2026-10-08に共通基盤・策定監査タスク・Skillを実装し、テスト環境で検証後、本番へ適用。以下は合意した設計で、実装仕様の正本はfbp-dsp Skill。検証・リリース結果は `database-security-policy-verification.md` を参照する。

## 目的と今回の範囲

DSPは、AIが生成・修正したアプリケーションコードの認可漏れを、共通データアクセス層で補完する仕組みとする。既存のfixed_file_manager（FFM）を利用し、既存アプリケーションの互換性を優先する。

代表例は「予約レコードを変更・削除できるのは登録した本人と、その予約を管理する権限を持つ管理者だけ」である。画面・公開側・MCPの実装で確認を忘れても、FFMが保存済みレコードと認証情報を照合して拒否する。

今回の対象はinsert、get（一覧・検索を含む）、update、deleteと、それらの認証・権限判定、ロック整合性、例外・ログ、策定・監査タスク、Skill、テストとする。

直接ファイルアクセス、意図的なDSP無効化、ポリシーファイル改変、保守操作による迂回、OS権限・別プロセスによる隔離は今回の検討・実装対象にしない。DSPは任意のPHPコードを強制的に隔離する仕組みではない。

## 責務と配置

| 担当 | 責務 |
|---|---|
| フレームワーク | channelの確定、DSPの読み込み、FFMからの呼び出し、判定中のDB接続状態の固定、例外・ログ |
| プロジェクトのDSP | Controllerを利用した認証・所属・代理権限の確認と、対象データに対する許可・拒否 |
| policy.md | 人間とAIが読む業務ルール、対象、条件、例外、未確定事項 |

独立したContextProviderやDspExecutionContextは必須にしない。プロジェクトごとの複雑なログイン経路（本部・店舗・代理店など）は、DSPが既存の認証処理を利用して解決する。

共通のDspInterface、DspException、読み込み処理はフレームワークに配置する。プロジェクトには共通型を複製せず、次を配置する。

```text
classes/dsp/
├── policy.md
├── registry.php
└── ReservationDsp.php など
```

registry.phpは対象DBとDSPクラスの対応を宣言する。`class/table => ['file' => 'ReservationDsp.php', 'class' => 'ReservationDsp', 'dependencies' => [...]]` の配列を返す。共通型はfbp/interface/DspInterface.php、fbp/lib/DspException.phpとDspReadDecision.phpに配置する。物理分割領域の完全一致を優先し、Controller経由では論理クラスの登録を分割領域にも適用する。

現在の同期処理は主にfbpとclasses/appを対象とするため、classes/dspの同期・配布・リリース対応が必要。環境固有の手順は環境ルールを参照する。

## Controllerとchannelの受け渡し

ポリシーの生成規約は次とする。

```php
public function __construct(Controller $ctl, string $channel)
```

コンストラクタは依存の保持のみを行い、DBアクセスや権限判定をしない。認証・所属・権限は各操作の判定時に取得し、生成時の情報を固定しない。

channelはフレームワークが実際の入口から確定する。候補はadmin、public、mcp、api、cron、cli。クライアントの自己申告や現在の実行クラス名から判定しない。内部で別クラスを呼んでも入口のchannelは維持する。各DSPがchannelを見るかどうかは個別に設計できる。

channelは権限そのものではない。管理画面経由であっても管理者権限は別に確認する。管理者権限は、可能なら単一のis_adminではなく対象店舗・組織について判定する。

実装済みの`Controller::get_dsp_system_subject()`は、通常APIのHMAC認証成功後に`kind=api, verified=true`を返す。再認証開始・失敗・設定例外では古い証明を破棄する。cronは復号した実行IDと現存ジョブを確認し、実行中だけ`kind=cron, verified=true, job_id`を渡してfinallyで元に戻す。`set_dsp_system_subject()`はframeworkの検証済み実行経路用であり、GET/POST・ポリシー判定・利用者の自己申告から設定しない。プロジェクトはこの証明と対象範囲を照合して、自動処理の権限を定める。CLIに自動で証明を付与しない。

本人の所属と代理操作先は区別する。入力された店舗ID・組織IDを採用する場合は、所属・委任関係を検証する。管理ユーザー、サービス会員、OAuth主体などでID空間が異なる場合は、予約の登録者と同じ主体種別・ID空間で比較する。

FFMはDB単位でキャッシュされるため、DSPを別channelへ使い回さない。channelと認証情報の対応を保ち、登録済みDSPに必要な情報を解決できなければ安全側に停止する。

## FFM連携と共通インターフェイス案

コンストラクタの既存optionsを拡張し、引数・返却値の互換性を維持する。Controllerのdb()では現在FFM生成後にControllerを設定しているため、DSP用のControllerとchannelは生成時に渡せるようにする。

各呼び出し元でDSPを指定する方式にはせず、登録から対象のポリシーを自動解決する。通常のController経由以外のFFM生成経路についても、Controller・channelの提供方法を調査する。Controller未生成の初期化処理については、認証前の状態を通常ユーザーや管理者として扱わない。

操作別のメソッドは次とする。読み取り要求にはmethodと、そのAPIのid/ids、itemname/value、sortitem/sort_order、maxなどの引数を含める。

```php
interface DspInterface
{
    public function authorizeInsert(array $newRow): void;
    public function authorizeRead(array $request): void;
    public function inspectRead(array $row): DspReadDecision;
    public function authorizeUpdate(
        array $before,
        array $after,
        array $submittedFields
    ): void;
    public function authorizeDelete(array $before): void;
}
```

authorizeReadは取得メソッド・検索条件・ソート条件などを検査する。DspReadDecisionは行の可視性と返却可能な項目を表す案とし、項目除外はFFMが実施する。

### 読み取り

- get/select/filterだけでなく、getall、get_many、next、before、match、neighbors系、iterate_filterも対象にする。
- 操作自体の禁止、ID指定による禁止対象へのアクセスはDspExceptionとする。
- 一覧ではポリシーで定めた可視行だけを返す。これは違反の見逃しではなく、許可範囲の選択とする。
- 可視行の選別は件数制限・ページ判定より前に行い、項目除外は内部検索・ソートなどの後に行う。
- 非公開項目による検索・ソートは原則拒否し、必要な例外は明記する。
- 索引・高速検索経路でも同じポリシー結果とし、コールバックへ渡す行も返却制限を適用する。
- 各APIの配列形式、キー、null、参照引数is_lastなどの既存契約を維持する。

### insert/update/delete

FFM内部の生データ取得と、アプリへの公開読み取りを分ける。現行のupdate/deleteは公開get()を利用しているため、返却項目の制限された行を更新前データとして使わない。

```text
必要なDBを事前オープン
  → ロック確定後に対象データを内部取得
  → 保存予定値を生成
  → DSP判定（DB接続状態を固定）
  → 許可された場合だけログ・データ・索引を更新
```

updateは既存の部分更新を維持し、更新前・更新後・指定された項目を検査する。文字切り詰め・数値変換など、保存時の変換後の値とDSPが検査する値を一致させる。insertの拒否時は最大ID、呼び出し元へのID反映、操作ログ、索引に変更を残さない。

例外時も必要なファイルポインタ・ガード状態を復元する。複数DB更新の一括ロールバックは現行FFMの保証に含まれず、DSP追加によって保証されるとは扱わない。

## 判定中のDB接続ガード

Controllerに次の共通機能を追加する案とする。

```php
set_prohibit_new_db(bool $flag)
get_prohibit_new_db(): bool
```

禁止中は既に開いているDBの取得だけを許可し、未オープンのDBはFFM生成前に例外とする。別クラス・別分割領域のDBも別DBとして判定する。

このフラグは接続状態の固定に使い、通常処理では既存DBへの認可された更新を許可する。DSP判定の実行状態はDspRuntimeが別に管理し、判定中だけFFMの書き込みを禁止する。Controllerを渡した直接のFFM新規生成も接続ガードで拒否する。

```php
$previous = $ctl->get_prohibit_new_db();
$ctl->set_prohibit_new_db(true);
try {
    $policy->authorizeUpdate($before, $after, $submittedFields);
} finally {
    $ctl->set_prohibit_new_db($previous);
}
```

入れ子の処理に対応するため、解除は常に元の状態へ復元する。DSPの権限確認に必要なDBはregistryのdependenciesにtable、class、必要ならseparated_byを宣言して事前に開き、判定中は読み取りだけを行う。依存の循環は読み込みエラーとして停止する。

判定中は新規DBオープンだけでなく、Controller経由のDBクローズとロック解除を伴う処理も停止させる。現行のController::api()は外部通信時に全DBのロックを解除・再取得するため、その処理もガード対象とする。これは通常処理のロック整合性を保つための措置であり、意図的な迂回対策ではない。

現行check_hf()は閉じたハンドルを再オープンせず、例外にする。既存FFMのロック順序、再取得、整合性管理は維持する。

## 予約ポリシー例

- 登録: 認証済み本人と新規レコードの登録者が一致する。
- 更新・削除: 保存済み予約の登録者本人、または対象店舗の予約管理権限を持つ利用者だけ許可する。
- 更新: 登録者IDの変更は禁止する。この例では管理者も変更できない。
- 本人判定: リクエスト中の登録者IDではなく、保存済みレコードの登録者と照合する。
- 参照権限、管理者による代理登録、所有者変更、channelごとの差異は別の業務ルールとして確認する。推測で追加しない。

認可条件はReservationDspに明示し、既存ヘルパーは認証情報・所属関係の取得を中心に再利用する。通常はpolicy.mdとDSPクラスを見ればルールを確認できる構成にする。認証情報の正しさとFFMによる確実な呼び出しは共通基盤側で別途検証する。

## 段階的導入とエラー

| 状態 | 動作 |
|---|---|
| DSP未定義 | 既存動作を維持 |
| 定義済み・許可 | 継続 |
| 定義済み・違反 | DspException |
| 定義済み・実装欠落、読み込み失敗、判定エラー | 安全側に停止し内部記録 |

読み込み・判定エラーを未定義へ落とさない。新しいDBにDSPがないことだけでは拒否しない。将来の必須化を妨げない構成にするが、今回は有効化しない。

DspExceptionの外部向けメッセージには機密情報を含めない。内部では操作、対象識別子、ルールID、理由コード、実行主体、channel、ポリシー版、追跡IDを記録する。行の全内容は原則記録しない。通常の違反と読み込み・判定エラーは区別する。

## DSP策定・監査タスク

「AIに依頼する」の最初の画面に、Database Security Policy策定とDatabase Security Policy監査を追加する。既存のタスク管理・AI実行・報告フローを再利用し、画面、保存時検証、タスクAPI、実行工程まで専用種別を扱う。種別番号は既存定義を確認して確定する。

策定ではデータ構造、認証・権限、通常のアクセス経路を調査し、既存ポリシーを維持しながら変更の必要性を判断する。policy.mdと実装、許可・拒否テストを作成し結果をタスクへ報告する。不明な業務ルールは確認事項として報告する。既存のコード変更・リリース許可を尊重する。

監査ではpolicy.mdとPHP実装の整合性、通常のFFMアクセスへの適用漏れ、認可漏れ、項目制御、許可・拒否結果を確認する。DSP未定義DBを適用候補として一覧化する。今回対象外とした意図的な迂回経路の調査は要求しない。

監査は原則読み取り専用とし、修正指示がない限りコード変更・同期・リリースを行わない。書き込みの許可・拒否テストは使い捨てデータまたは隔離したテスト環境で行い、実データに対して「拒否されるはず」の操作を試さない。

## policy.mdとSkill

policy.mdには対象DB、主体種別、許可・禁止操作、可視行、返却項目、変更可能項目、判定条件、対象組織・代理権限、channel差異、例外、関連DB、ルールID、未確定事項、テスト対応を記載する。

fbp-dsp Skillに、設計思想、共通インターフェイス、Controllerとchannelを受け取る実装パターン、FFM連携、事前DBオープンとガード、policy.md、例外・ログ、テスト・監査、段階的導入をまとめた。app-soshikikaikakuの例はテスト専用DBだけへ適用し、既存業務ルールを推測で変更しない。

## 検証計画と実装順

最低限、未定義時の互換性、許可CRUD、違反時の例外、他ユーザー・他組織の拒否、禁止項目の更新・取得拒否、読み込み・判定エラー、ロックとデータ整合性を検証する。

追加で全読み取りAPI、索引あり・なし、ページ判定、保存時変換、Controller以外の通常FFM生成経路、channel維持、関連DB事前オープン、ガードの入れ子・例外復元を確認する。排他は別プロセスの同時実行で検証する。対象外の保守操作・意図的な迂回の検証は今回要求しない。

### FFM単体の1,000パターンテスト

実装完了条件として、既存のFFM単体テストに加え、異なる条件を持つ1,000パターン以上のテストを実施する。同じケースの反復や個々のassert数をパターン数に数えない。ケースID、入力条件、期待結果、結果を一覧化し、生成ケースは固定seedで再現可能にする。既存のtests/run.phpや差分比較シナリオを活用する。

予定するケース配分は以下とする。実装で必要なケースが増えた場合は追加し、必須条件を件数合わせで省略しない。

| 分類 | パターン数 | 主な内容 |
|---|---:|---|
| DSP未定義の互換性 | 250 | CRUD、データ型、部分更新、検索・ソート・件数制限、既存返却形式。変更前との比較 |
| insert認可 | 100 | 本人、未認証、他人の登録者指定、所属条件、保存時変換、拒否時の無変更 |
| 読み取り認可 | 250 | 全読み取りAPI、可視行、非公開項目、検索・ソート条件、索引あり・なし、ページ判定 |
| update認可 | 200 | 本人、対象組織の管理者、他人・他組織、禁止項目、所有者変更、部分更新、保存予定値 |
| delete認可 | 100 | 本人、対象組織の管理者、他人・他組織、状態条件、対象なし、拒否時の無変更 |
| 読み込み・判定・ガードの異常 | 50 | 実装欠落、判定例外、必要な認証情報の欠落、新規DB禁止、入れ子、例外時復元 |
| 排他・整合性 | 50 | 別プロセスの競合、関連DB事前オープン、更新の取りこぼし、拒否後のデータ・索引・ID整合性 |
| 合計 | 1,000 | |

期待結果は実装の出力から自動採用せず、業務ルール・既存仕様から定義する。互換性は変更前の実装との比較、認可は独立した期待結果、整合性は再オープン後のデータ・索引・ヘッダ確認などで検証する。テスト用データ領域を使い、業務データを破壊しない。

### app-soshikikaikakuテスト環境での最終確認

フレームワークの単体・回帰テスト後、app-soshikikaikakuのテスト環境に実装を反映して最終統合テストを行う。本番環境には反映しない。

- DSP未定義の既存機能について、管理画面・公開側・MCPの代表的な利用経路とCRUDを回帰確認する。
- 専用の安全なテスト用ノート・データ・主体を用意し、本人、対象組織の管理者、他人、他組織、未認証の許可・拒否を確認する。未確定の業務ルールを既存ノートへ推測で適用しない。
- Controllerとchannelの受け渡し、DB接続ガード、返却項目、保存済み所有者による判定を確認する。
- 「AIに依頼する」のDSP策定・監査の登録・種別・実行範囲・結果報告を確認し、監査でコード変更やリリースが発生しないことを確認する。
- 対象アプリのdocs、定義、既存権限を調査して具体的な対象と期待結果を確定する。入口が利用不能の場合は未検証を明記し、成功扱いにしない。

最終報告には1,000パターンの実行数・成功数・失敗数・未実行数、ケース分類、再現方法、統合テスト結果、残課題を記載する。必要なチェックの失敗・未検証が残る間は検証完了としない。実行結果と確認の限界はdatabase-security-policy-verification.mdとdsp-test-results.jsonに記録した。

実装は共通型と読み込み方式、Controllerのchannel・ガード、FFM連携、プロジェクトの実装例、策定・監査タスク、Skill、互換性・セキュリティーテスト、docs更新の順に進める。既存動作へ重大な影響が見つかった場合は報告して設計を見直す。
