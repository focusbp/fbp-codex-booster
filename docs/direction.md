# 開発方針・進行中の作業

## 2026-10-30 Excel風画面からAIへ機能追加を依頼する入口

### 目的と現在地

利用者が依頼文を一から考えなくても、典型的な機能を選び、必要な説明を補うだけでAIへ実装を依頼できるようにする。依頼の敷居を下げるとともに、Codexが情報不足による聞き直しや実装方法の探索に時間を使わず着手できるようにする。

初期段階で要件理解と進め方を合意。その後、利用者の指示により専用検証アプリで下記7機能のサンプルを実装・検証し、再利用資産と必要情報の一覧をサンプルSkillへ整備した。依頼受付「＋」UI・タスク登録・機能カタログ本体の実装と本番反映はまだ行っていない。

### 合意した利用者の操作

1. Excel風画面の表の上にあるページボタンエリアの右端へ「＋」アイコンを配置する。
2. 「＋」をクリックすると、典型的な機能のリストを表示する。
3. 機能を選ぶと、編集可能なテキストエリアに依頼内容の定型文を挿入する。
4. 利用者が必要に応じて編集し、「実行」するとプロジェクトサポートへ新規タスクを追加する。
5. 登録成功後、「AIに実装を依頼しました。進捗は下記からご覧ください」と表示し、プロジェクトサポートのURLを案内する。

「＋」は機能追加の依頼を作る入口。そのクリックだけで対象機能の実装が完了するものではない。

機能リストの候補：CSVアップロード、CSVダウンロード、PDF一覧印刷、MCP連携、フォーム作成（公開側）、単品ショップ作成（公開側）、AI-OCR読み込み。候補すべてを初回から実装することは未決定。

### 合意した進め方

UIより先に、Codex側の実装手順と必要情報を整理する。

1. 既存Skill・実装テンプレートを確認し、典型機能ごとの実装手順と不足する共通部品を整理する。
2. 各機能について、自動取得できる情報、利用者の入力が必要な情報、省略時の既定動作を決める。
3. UIとCodexが共有する機能カタログを設計する。機能ID、表示名、依頼の定型文、必要項目、適用するSkillを対応させる。
4. 対象プロジェクト・ノートなどの実装コンテキストを、編集可能な依頼文とは別の構造化情報としてタスクへ渡す方式を検討する。
5. カタログに沿って選択・依頼文編集・タスク登録・進捗案内のUIを作る。

当初はCSVダウンロード1種類から依頼経路を通す案だったが、利用者の追加指示で先に7機能の実装サンプルを作成する進め方へ変更した。タスク登録の経路は引き続き未実装。

### 確認済みの既存機能

- Excel風画面には、追加ボタン設定（`db_additionals`）の一覧上部（`place=0`）を表の上へ描画する処理がある。
- 取得処理は `fbp/app/db_exe/ExcelGridActions.php` の `excel_page()`、表示は `fbp/app/db_exe/Templates/excel.tpl` の `excel-toolbar`。
- この確認はソース上の確認。今回、実画面の表示・操作検証は行っていない。
- 既存設計は [Excel風標準画面の設計](excel-style-standard-screen-design.md) を参照する。実装時は対応するSkillを正本として確認する。

### 次回の着手点・未決事項

- CSVダウンロードを題材に、既存Skillとタスク受付・実行の経路を調査し、必要情報と依頼データの形式を具体化する。
- 対象プロジェクト・ノート・項目定義の取得方法と、タスクへ渡す情報の範囲を決める。
- プロジェクトサポートへの登録方法、登録者・実行権限、進捗URLの生成元を確認する。
- 登録失敗時の表示、二重送信防止、タスク登録後の実装・検証・リリースの扱いを既存運用に合わせて決める。「実行」が本番リリースまでの許可を含むとはまだ決めていない。
- 自由文以外に選択項目を設けるか、「＋」の表示対象、初回公開する機能の範囲、機能カタログの保存形式は未決定。

### サンプル整備の結果と追加要件

- CSV入出力・PDF・MCP・公開フォーム・単品ショップ・AI-OCRの7サンプルを専用検証アプリへ実装。再利用資産、明示的な導入ツール、機能別必要情報、検証手順は `fbp-app-samples` の [note-feature-samples](../fbp/docs/.agents/skills/fbp-app-samples/references/note-feature-samples.md) に集約した。
- 単品ショップは利用者指定でSquare Sandbox決済まで含め、ブラウザーのテストカード入力と決済成功を確認。
- OCRは利用者指定で現在のExcel列の名称・型・選択肢に合わせる動的方式。後から増えた列も反映し、計算/関数列を除外する。読み取り→確認修正→保存まで実画像で確認し、列追加追随・処理中の定義変更拒否は隔離モックで確認した。
- MCP OAuth PKCE・catalog・関数呼出しと検証トークン失効を確認。CSV実入出力、PC/スマホPDF、公開フォーム保存も確認済み。本番反映はしていない。
- 次は7つのサンプルから機能カタログと依頼データを具体化し、プロジェクトサポートへの受付経路を調査する。UI作成や自動タスク登録への着手は別途進め方を合意する。

### 商品サンプルの列順統一

利用者承認のテスト専用例外で商品サンプルをExcel化し、既存5件を保持。CSV・PDF・MCP・OCR・ショップ商品表示を実行時の列順に統一した。列移動後も価格などの業務上の対応が変わらないことを確認。通常のExcel定義保護と本番は変更せず、移行用一時処理は撤去した。

### Developer Modeと配布方向の更新

利用者が通常のDeveloper Mode編集を許可する方針へ変更。手動とCodexのCLIで標準↔Excel風・列設定を変更できる。本番同期は本番→テストの上書き、定義配布はテスト→本番へ統一し、テスト側で整えた修正をリリース直前の同期で消さない。詳細と検証は変更履歴を参照。

## 2026-10-30 機能追加「＋」UIと受付

- 9機能のサンプルを機能カタログへ統合し、最後に任意依頼の「その他」を追加。その他の定型文は対象ノート名＋「に下記の機能を追加してください。」＋空行。
- Excel風の表上部右端に「＋」を配置。ログイン済みでノート閲覧権限がある管理者が利用でき、機能選択→必要設定確認→必要情報と依頼文の編集→実行→プロジェクトサポートURL案内の順。単品ショップは商品名・価格（税込円）を必須にする。
- Square/OpenAI/SMTP/POP・IMAP/MCPの必要設定が不足する場合は登録を止める。設定権限があるユーザーには設定入口、一般ユーザーには管理者への依頼を案内。秘密値や実レコードは依頼に含めない。
- 利用者の指定により依頼範囲は実装・検証・本番リリースまで。画面に明示し、作成タスクの両許可を有効にする。対象ノートの現在の項目・型・順序と必要なSkillを、編集可能な依頼文とは別の構造化情報で渡す。
- 受付はアプリごとのHMAC認証と本文ハッシュを使い、登録先プロジェクトは管理側の台帳から解決する。同一受付番号の並行再送は同じタスクを返し、依頼変更は拒否する。長いコンテキストは履歴へ分割して保持する。
- カタログの正本はframeworkのconfig/note_feature_catalog.json。管理側には同じJSONを配布スナップショットとして同梱し、受付APIの反映に共通framework全体の配布を要求しない。
- 実画面のPC/スマホ、その他の初期文、ショップ必須情報、一般ユーザー・未ログイン・偽装トークン・不足設定・重複操作の隔離テスト、実FFMの並行再送、実DSP付きの作成/再送/履歴/件数更新を検証。実運用のサポートタスクは検証のためには作成していない。
- テスト環境へ反映済み。実運用でタスク登録を使うには管理側受付APIの本番反映が必要。共通frameworkの全体配布と実運用API反映は未実施。

- 最終の権限方針：ノート新規作成＋、機能追加依頼＋、データベース形式への変換は管理者限定。非管理者は非表示とし、直接呼出しも拒否。通常の行追加・データ編集は今回の構成操作の制限と分ける。隔離した実CLI環境で両ロールの表示・直接呼出し・ノート不変を検証済み。
