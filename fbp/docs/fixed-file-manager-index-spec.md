# fixed_file_manager インデックス仕様・テスト計画

## 1. 文書の位置づけ

この文書は、`fixed_file_manager` に任意項目のインデックスを追加するための仕様と、実装前後に必要なテストケースを定義する。

本仕様に基づく初期実装を追加済みである。既存プロジェクトとの検索結果・更新動作・データ形式の整合性を最優先する。

## 2. 目的

- `parent_id` などの完全一致検索で `.dat` 全件走査を避ける。
- 既存の `FFM` インターフェースと呼び出しコードを変更しない。
- インデックスが利用できない場合も、従来の全件検索で正しい結果を返す。
- `.dat` を唯一の正本とし、インデックスは再生成可能な補助データとして扱う。

## 3. 前提

- この機能を含むフレームワークから、未対応の古いフレームワークへ戻す運用は行わない。
- `.fmt` の変更により既存の `changeFormat()` が動作することを許容する。
- `IDX` の追加・削除時に `.dat` が変換されてもよい。
- DB管理ノートの `.fmt` は、DB項目定義から再生成する仕組みを正本とする。

## 4. `.fmt` 仕様

### 4.1 書式

従来の3項目形式に加え、第4項目へ `IDX` を指定できる。

```text
name,size,type
name,size,type,IDX
```

例:

```text
id,24,N
parent_id,24,N,IDX
status,24,N,IDX
name,300,T
```

### 4.2 検証規則

- 3項目または4項目だけを許可する。
- 第4項目は大文字の `IDX` だけを許可する。
- 未知のオプション、空の第4項目、5項目以上はフォーマットエラーとする。
- `id` に `IDX` が指定されてもエラーにはせず、インデックス作成対象から除外する。
- `id` は従来の二分探索を使用する。
- `.fmt` の文字列は `IDX` を含めて `.dat` ヘッダーへ保存する。
- `IDX` の追加・削除はフォーマット変更として扱い、既存の `changeFormat()` を実行してよい。

不正例:

```text
parent_id,24,N,INDEX
parent_id,24,N,idx
parent_id,24,N,
parent_id,24,N,IDX,OTHER
```

## 5. DB項目定義

DB管理ノートでは、`.fmt` を直接編集しない。DB項目定義にインデックス指定を保持し、画面およびCLIの `.fmt` 再生成処理から `IDX` を出力する。

初期仕様では、DB項目定義に次の値を持つ。

```text
index_flag
0: インデックスなし
1: IDX
```

`index_flag=1` の項目は次の形式で出力する。

```text
parameter_name,length,type,IDX
```

`id` はDB項目定義に指定があっても無視する。親子関係から自動生成された `parent_id` も、明示的に `index_flag=1` が設定された場合だけインデックス化する。

## 6. 初期実装の対象

初期実装は完全一致検索の候補ID取得に限定する。Standard Screen対応後は、`filter()`が`exact_match=false`でも、AND条件内の`N`型・`=`条件だけを索引候補の絞り込みに利用する。

- `select()` の一致演算子 `=`
- `filter()` の `exact_match=true`
- `filter()` の `exact_match=false`に含まれる`N`型・`=`条件（Standard Screenのdropdown、radio、number等）
- `T`、`N`、`F` 型の単一値
- 単一条件、またはAND条件中のインデックス対象条件
- `parent_id` を最優先の利用対象とする

索引で候補IDを取得した後、既存の条件判定を必ず再実行する。インデックスだけで最終結果を確定しない。

次は初期実装でインデックスを使わず、従来検索へ戻す。

- 部分一致検索
- `filter()` の `exact_match=false`に含まれる`T`・`F`・`A`型、配列項目、範囲条件
- `A` 型
- 範囲比較 `<`、`<=`、`>`、`>=`
- インデックスだけでは安全に候補集合を決定できないOR条件
- 不正、欠落、更新途中、または形式不一致のインデックス

## 7. 検索互換性

インデックス有無によって、次の外部仕様を変更しない。

- 戻り値の行と各項目
- 戻り順
- `SORT_ASC` / `SORT_DESC`
- 同じソート値を持つ行の順序
- `max`
- `is_last`
- AND / OR
- `0` と空値の扱い
- 数値と数値文字列の比較
- 削除済み行の除外
- `_id_enc` の付加
- 例外条件とエラー内容

インデックス経路は、候補IDを既存走査順と同じID降順で扱い、最終的な条件判定・ソート・件数制限を従来処理と共通化する。

## 8. インデックスファイル

- `.dat` と同じデータ領域に、`<datパス>.<項目名>.idx/` という索引ディレクトリを置く。
- 索引は固定で128 shardとし、`manifest.bin`と`000.bin`〜`127.bin`で構成する。
- 検索値を項目型とともにSHA-256へ正規化し、先頭7 bitでshardを決定する。
- shardは、32-byte検索値ハッシュ、64-bit ID領域offset、ID件数からなる固定長ディレクトリと、64-bit ID配列を保持する。
- 検索時は該当shardの固定長ディレクトリを二分探索し、一致したID範囲だけを`fseek()`で読む。索引全体はPHP配列へ展開しない。
- manifestと各shardには形式バージョン2を持たせる。
- レコードのファイル位置ではなくIDを保持する。
- `.dat`、`.fmt`、操作ログ、バックアップを正本とし、索引ファイルはバックアップ復旧の必須データにしない。
- 索引ファイルがなくてもアプリケーションは動作する。

索引メタ情報には最低限、次を保持する。

- 索引形式バージョン
- テーブル名
- 項目名
- 項目型
- `.fmt` のハッシュ
- `.dat` の最大ID
- 登録ID数
- shard数
- 全128 shardのSHA-256

各shardのヘッダーには、形式バージョン、shard番号、検索値数、ID数、テーブル・項目・型・`.fmt`を結び付けるidentityを保持する。オープン時はmanifestと全shardのヘッダー・ファイルサイズ・ID数合計を検査し、実際に検索するshardは初回利用時にSHA-256を検査する。

旧形式の単一JSON索引は正本ではないため、書込み可能なオープン時に`.dat`から128分割バイナリ索引へ再構築する。read-only時は変換せず全件検索へ戻る。

## 9. 更新と障害時の整合性

`.dat` のロックを保持している間に、対応する索引を更新する。別のロック順序を増やして既存の複数DBロック順を壊さない。

次の操作を索引更新対象とする。

- `insert()`
- `update()`
- `delete()`
- `restore_deleted_record()`
- `allclear()`
- `changeFormat()`

更新途中を識別するため、テーブル単位のdirty状態を使用する。

1. 索引更新前にdirty状態を作る。
2. `.dat` を更新する。
3. 変更値に対応するshardだけを一時ファイルへ書き、正式shardへrenameする。
4. shardのSHA-256と件数を反映したmanifestを一時ファイルからrenameする。
5. 全対象索引の更新後にdirty状態を解除する。

索引の新規構築と再構築は、128 shardを一時ディレクトリに作成してからディレクトリ単位で切り替える。非索引項目だけのupdateではshardを書き換えない。

dirty状態、索引欠落、メタ情報不一致、読込エラーを検出した場合は、そのリクエストでは索引を使わず従来検索を行う。壊れた索引を理由に通常のCRUDや検索を失敗させない。

`changeFormat()` 完了時は、新しい `.fmt` にある `IDX` 定義を正本として索引を再構築する。`IDX` が削除された項目の索引は使用しない。

## 10. テストプログラム

テストは次の場所に置き、CLIから実行する。

```text
fbp/lib/fixed_file_manager/tests/run.php
```

必要に応じて同じディレクトリ内でケース別ファイルへ分割する。Web経由で実行されないよう、全入口で `PHP_SAPI === "cli"` を必須とする。

テストデータはランダム名の一時ディレクトリに作成し、既存プロジェクトの `.dat`、`.fmt`、索引を直接変更しない。実データを使う互換テストでも、対象ファイルを一時領域へコピーしてから実行する。

## 11. テストケース

### 11.1 フォーマット解析

- 従来の3項目形式を読み込める。
- `IDX`付き4項目形式を読み込める。
- `IDX`の有無がフィールド情報へ反映される。
- `id,24,N,IDX`を読み込めるが、索引対象から除外される。
- 未知の第4項目を拒否する。
- 小文字`idx`を拒否する。
- 空の第4項目を拒否する。
- 5項目以上を拒否する。
- 既存の名前・サイズ・型検証が維持される。

### 11.2 `changeFormat()`

- 3項目形式から`,IDX`追加時に`changeFormat()`が正常完了する。
- `IDX`削除時に`changeFormat()`が正常完了する。
- `IDX`追加・削除の前後で全有効行のデータが一致する。
- 最大IDが維持される。
- 削除済み行の扱いが従来と一致する。
- `IDX`と同時に項目追加・サイズ変更・型変更を行える。
- 同時に複数プロセスが新しい`.fmt`を開いても、既存のフォーマット変更ロックでデッドロックしない。

### 11.3 インデックス構築

- 空データから空索引を作成できる。
- 1件および複数件から索引を作成できる。
- 同じ値を持つ複数IDを保持できる。
- `0`、負数、大きな数値、空文字、日本語、前後空白を正しく扱う。
- 削除済み行を索引結果へ含めない。
- `id`の索引を作らない。
- 複数の`IDX`項目を個別に構築できる。

### 11.4 検索結果比較

各ケースで、索引OFFの従来検索結果と索引ONの結果を厳密比較する。

- `parent_id`完全一致
- 存在しない値
- 単一条件
- 複数AND条件
- OR条件のフォールバック
- T/N/F型
- 数値と数値文字列
- ID昇順・降順
- 別項目による昇順・降順
- 同一ソート値
- `max`が結果件数未満、同数、超過
- `is_last`の真偽
- `set_flg_filter_zero()`有効・無効
- `_id_enc`付加環境
- Standard Screen相当の`exact_match=false`で、N型完全一致、0、N型＋T型部分一致、N型範囲条件

### 11.5 CRUD追従

- insert直後に索引検索できる。
- indexed fieldを変更するupdateで旧値から消え、新値へ移る。
- indexed fieldを変更しないupdateで索引結果が変わらない。
- delete直後に索引結果から消える。
- restore_deleted_record直後に索引結果へ戻る。
- allclear後に索引結果が空になる。
- 複数IDX項目が同時に正しく更新される。

### 11.6 異常・復旧

- 索引ファイルが存在しない場合に全件検索へ戻る。
- 索引ファイルが空または壊れている場合に全件検索へ戻る。
- 索引メタ情報のバージョン不一致で全件検索へ戻る。
- `.fmt`ハッシュ不一致で全件検索へ戻る。
- dirty状態が残っている場合に全件検索へ戻る。
- 索引一時ファイルだけが残っている場合に全件検索へ戻る。
- 索引書込み失敗時も`.dat`の正しい検索結果を返せる。
- プロセス強制終了後、再オープンして全件検索できる。
- 索引再構築後に索引OFF/ONの結果が一致する。

### 11.7 同時実行

- 複数プロセスから同時検索する。
- 検索とinsertを並行実行する。
- 検索とupdate/deleteを並行実行する。
- 索引構築と検索を並行実行する。
- `changeFormat()`と索引利用を並行実行する。
- 子プロセスを更新途中で強制終了する。
- タイムアウトとデッドロックが発生しない。

### 11.8 既存プロジェクト互換

- 代表的な既存`.dat`と`.fmt`を一時領域へコピーする。
- コピーにのみ`IDX`を追加して`changeFormat()`する。
- 変換前後の全有効行を比較する。
- `parent_id`検索を索引OFF/ONで比較する。
- 既存の`select()` / `filter()`引数パターンを再現する。
- 小規模、削除行あり、日本語あり、数万件以上のノートを含める。
- 元の既存プロジェクトファイルのハッシュがテスト前後で不変であることを確認する。

### 11.9 性能測定

- 1千、1万、10万件で測定する。
- 索引構築時間を測定する。
- 完全一致検索を索引OFF/ONで比較する。
- 一致件数1件、少数、多数で比較する。
- insert、indexed field update、deleteの追加コストを測定する。
- 索引ファイルサイズとメモリ使用量を記録する。

### 11.10 変更前・変更後の差分テスト

インデックス実装直前のGitコミットを基準版として固定し、基準版の `fixed_file_manager.php` と変更後の実装を同じテストランナーから切り替えて実行する。基準版と変更後版は、それぞれ独立した一時データ領域を使用する。

- 基準版のコミットIDと対象ファイルのSHA-256をテスト結果へ記録する。
- 同一の3項目`.fmt`、初期データ、操作列を基準版と変更後版へ与える。
- `insert`、`get`、`getall`、`select`、`filter`、`update`、`delete`、`restore_deleted_record`、`allclear`の戻り値と最終状態を比較する。
- 検索結果は行、型、順序、`max`、`is_last`、例外の種類とメッセージを厳密比較する。
- `IDX`なしの3項目`.fmt`では、操作後の`.dat`をSHA-256およびバイト単位で比較する。
- `IDX`なしでは、変更後版が索引・メタ・dirty・一時ファイルを作成しないことを確認する。
- 操作ログは時刻、PID、txidなどの変動値を除いて内容を比較する。
- フォーマット変更前後の有効行、最大ID、削除状態を比較する。
- 代表的な既存プロジェクトのデータコピーでも、基準版と変更後版の結果を比較する。
- 1千、1万、10万件で基準版、変更後IDXなし、変更後IDXありの時間とメモリを比較する。

基準版はテスト時にGitから一時領域へ取り出し、フレームワーク内へ旧実装のコピーを恒久配置しない。これにより、テスト専用のFFM実装が本体と二重管理されることを防ぐ。

`IDX`付き4項目`.fmt`は基準版が解析できないため、次の2系統に分ける。

1. 基準版対変更後版: 従来の3項目`.fmt`で後方互換を確認する。
2. 変更後版の索引OFF対索引ON: `IDX`付き4項目`.fmt`で検索結果の同一性を確認する。

## 13. 初期導入方針

1. テストプログラムを先に作る。
2. `.fmt`の4項目解析と`changeFormat()`互換を実装する。
3. 索引構築と索引OFF/ON比較を実装する。
4. CRUD追従と異常時フォールバックを実装する。
5. 既存プロジェクトのコピーで互換テストする。
6. 開発環境の選択した`parent_id`項目だけに`IDX`を付ける。
7. 十分な検証後に対象を拡大する。

初期段階では、既存プロジェクトの`.fmt`へ一括で`IDX`を追加しない。

- read-only時は破損索引を変更せず全件検索へ戻り、書込み可能な再オープン時に自動再構築すること
- manifestのversion、shard数、最大ID、`.fmt`ハッシュ、identity不一致の検出と自動再構築
- shard欠落、切詰め、shard番号不一致の検出と自動再構築
- shardのSHA-256不一致を検索時に検出し、全件検索へ戻してdirtyを残すこと
- Standard Screen相当のN型完全一致で、対象shard破損時に全件検索へ戻してdirtyを残すこと
- 3 writer・3 readerの並行実行と、終了後60件の全件比較
- 5プロセスによる同時`changeFormat()`と検索

manifestまたはshardの構造不整合は、書込み可能なオープン時に`.dat`から自動再構築する。read-only時は索引を書き換えず全件検索へ戻る。オープン時の軽量検査を通過したshardでも、検索時のSHA-256不一致は内容破損の可能性があるためdirtyを残し、自動的に正常扱いしない。

ただし、dirtyは`.dat`書込み途中の異常終了を示す可能性があるため、自動的にdirtyを消して正常扱いにはしない。dirty中は全件検索を維持し、明示的な整合性確認・再構築を必要とする。

## 20. Standard Screen数値検索対応

Standard Screenの`db_exe::rows()`は、文字列の部分一致を維持するため`filter(..., exact_match=false)`を使用する。この呼出し全体を完全一致扱いへ変更せず、AND条件内で索引を安全に使える`N`型・`=`条件だけから候補IDを取得し、従来の条件判定で全条件を再確認する。

- dropdown、radio、number、親IDなど、`.fmt`上で`N`型かつ検索演算子が`=`の項目だけが対象。
- T型の部分一致、F型、A型、日付等の範囲条件、OR条件は従来どおり全件検索する。
- N型完全一致とT型部分一致のANDでは、N型索引で候補を絞った後にT型部分一致を従来処理で判定する。
- 索引なし、dirty、欠落、破損時は従来の全件検索へ戻る。
- `IDX`なしの既存画面には変化がない。

2026-08-14の100万件・1,000種類の`parent_id`（一致1,000件）測定:

| 項目 | 結果 |
|---|---:|
| 全件検索 | 2.487848秒 |
| Standard Screen相当filter | 0.027545秒 |
| 短縮率 | 約90倍 |
| 検索時PHPピーク | 10 MiB |

基本差分テスト、異常系20件、既存5回帰テストはすべてPASSした。app-soshikikaikakuのStandard Screenでも索引ON/OFFの出力SHA-256は一致した。プロジェクト192件では画面処理全体が双方約0.30〜0.32秒であり、現時点では速度差より共通初期化処理が支配的だが、件数増加時には全件走査を避けられる。
