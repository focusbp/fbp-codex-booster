# 管理画面添付の認証・権限強化案

状態: 2026-11-11、管理側Standard Screenへの接続と専用テスト環境の検証後、利用者承認により6559e9dを配布対象3サーバーへ本番反映済み。リリース正常終了・配布元の主要ファイル一致・本番の未ログイン拒否と旧画像入口の応答を確認。目的は、正常な管理画面の見た目を保ったまま、添付取得にも画面と同じ認証・閲覧権限を適用すること。

## 接続・検証結果

- 別作業のフォーム表示準備（a27d2c9）完了後、db_exeの標準画面描画時だけサーバー所有の描画コンテキストを設定。共通部品はそのコンテキストと実クラスを確認して配信先を切り替える。公開側・独自画面・Original Screen・Excelの既存処理は維持する。
- 画像のsrc/hrefと添付のdata-urlを新経路へ接続し、管理側の描画ではget_file_infoによる暗号化pathの生成・出力を行わない。既存の画像寸法・DOMの外形・CSS・文言と、拡大/ダウンロード操作を維持する。
- 専用テスト環境の実ルーターとPlaywrightで一覧・編集・削除確認・子一覧・子編集・単一レコードを確認。表示準備フックによる非表示・読取り専用も確認した。標準画面のHTMLに旧data-path、旧db_exe画像URL、保存ファイル名が出ていないことを確認。
- 同じ行・同じCSSで旧/新部品を比較し、画像120×72px、添付リンク600×25.59375px、文言が一致。画像拡大と日本語ファイル名の実ダウンロードも成功。
- 新しい管理URLは未ログインで401、ファイルIDの差替えは404。既存の暗号化URLと公開用public_mediaは未ログインでも従来どおり200を確認。元のURLの失効・全経路の非公開化は行っていない。
- 単体55・実セッション/FFM/DSP8・隔離HTTP17の80項目に加え、上記実画面を確認。検証用ノート・添付・レコードは確認後に削除した。
- 今回の実画面検証は専用アプリの代表例。既存アプリ全件の独自管理アクセスガード・DSP・追加親子関係まで互換性を保証したものではない。独自ガードが新配信クラスを拒否する場合など、配布前に対象アプリの条件と照合する。新経路の認可は迂回させない。

## 先行実装と合流待ち

別Codexが標準画面を変更中のため、利用者指示により共有するdb_exe・標準テンプレート・フォーム処理には触れず、次を独立したファイルで実装した。

- `lib/StandardScreenMedia.php`: 対象識別URLの生成と、毎回の管理セッション・画面操作権限・visibility_filterの行条件・FFM/DSPの行/項目制限・legacy親子関係・ファイル所属・保存先・画像MIMEの確認。
- `app/standard_screen_media/standard_screen_media.php`: 管理用の独立した画像/ダウンロード入口。認証失効時は画像要求をログインHTMLへ転送せず401を返す。拒否はファイル実体を返さず、非公開応答はno-store。既存配信入口は未変更。
- `ManagementCsrf`に新入口のGET/HEAD読取りを登録し、POSTの既存CSRF検証は維持する。他の入口の扱いは変えない。
- 専用テストアプリのstandard_media検証資産で、隔離した実管理セッション/FFM/DSPとHTTP応答を確認（単体46・実認証/FFM/DSP8・HTTP17の計71項目）。標準画面自体の外観や旧path非露出は、まだ検証していない。

接続用APIは `StandardScreenMedia::url($ctl, $args, $image)`。`$args` はdb_id、row_id、field、screen、file_id、variant（original/thumbnail）。保存先path・旧tokenはURLへ入れない。resolveの戻り値はサーバー用で、テンプレートへそのまま渡さない。

screenはlist/list_on_side/edit/deleteを受け付け、標準画面の対応操作の認可を再確認する。addを既存レコードの取得許可には使わない。登録前の新規フォームは保存済み添付を持たず、複製等で既存添付を表示する場合は、元レコードの適切な閲覧コンテキストを接続時に決める。Excel・Original Screen・動的な追加親子関係は今回の先行実装対象外。任意の行判定が必要な場合の明示的拡張として、visibility_filterの任意メソッドcan_read_attachmentを呼べる（対象行・項目名・ノート設定を渡す。親の確認時は項目名が空）。既存の認可やDSPを迂回しない。

この先行段階の後、利用者の別作業完了連絡を受けて接続・専用環境の検証を完了した。結果は冒頭の接続・検証結果を正とする。本番反映と対象アプリ固有条件の確認は別工程。

## 確定した初回対象: 管理画面のStandard Screenのみ

利用者の確認により、初回は管理画面のStandard Screenに限定する。以下を接続完了時の受入条件とする。本番反映は別指示とする。

| 範囲 | 今回の扱い |
| --- | --- |
| 管理側の標準一覧・子一覧・詳細・登録・編集・削除確認・単一レコード画面 | 画像/ファイルの取得先を新しい管理用配信へ接続 |
| 上記からのサムネイル・元画像・拡大表示・ダウンロード | セッションと対象の閲覧権限を毎回確認 |
| 公開ページ・メール・LINE・独自画面・アプリ独自配信 | 既存の配信・URL生成を維持 |
| 旧暗号化URL・旧配信入口 | 存続。今回無効化・一括認証化しない |

- 標準画面が返すHTML・data属性・JavaScript・Ajax応答には、ファイル保存パスを含む旧暗号化URLや旧配信用path tokenを出さない。プレビューとダウンロードの両方が対象。画面に不要なファイル情報も応答へ混ぜない。
- 新URLはノート・レコード・項目・元画像/サムネイル等の識別情報を使う。これらを知っていても、取得時の有効なセッションと閲覧権限がなければ返さない。セッションIDや認証の代わりになる永続tokenをURLへ付けない。
- テンプレートを共有する公開側へ波及させないよう、標準画面のサーバー側描画処理が設定する明示的な描画コンテキストで分岐する。GET/POSTで任意に公開扱いへ切り替える設計にはしない。`get_APP_URL()` 全体や `get_file_info()` の既存契約を一括変更しない。
- 標準画面から旧URLが新たに露出する機会を減らすことが今回の効果。同じファイルの過去URLや別画面から生成された旧URLは残るため、ファイル全体の完全非公開化とは区別する。
- 外観の比較に加え、実際のHTML・Ajax応答・ネットワーク要求に旧path URL/tokenがないことを確認する。許可利用者の取得成功、未ログイン/失効/権限なしの拒否、公開側の従来表示の維持を確認する。

横断一覧の325候補を一括修正する計画ではない。標準画面の描画入口・共通部品の管理用分岐・管理用配信処理に変更を絞り、独自画面の移行は含めない。

## 2026-11-11 改訂方針: 管理側に別経路を追加し、公開側を維持

利用者提案により、最初の導入範囲を以下に変更する。この節を現行案とし、後続の一括した配信区分管理・迂回経路遮断は将来の強化案として扱う。

- 管理画面用にセッション認証・ノート/レコード/項目の閲覧権限を確認する専用の配信経路を追加する。管理側の標準表示・入力だけを新経路へ接続し、外観・操作を維持する。
- 公開側の既存暗号化URL、`db_exe` の既存配信、`upload/pull`、`public_media` は当面維持する。今回これらを一律にログイン必須へ変更しない。
- `get_APP_URL()` 等の横断一覧から公開利用と管理利用を切り分けて移行対象を決める。`get_APP_URL()` 全体の挙動を一律に変えない。動的指定や共通テンプレートは呼出元を追加確認する。[横断検索結果](attachment-url-inventory.md)を参照。
- 同じファイルの旧暗号化URLが有効な場合、ログインなしでの取得は従来どおり可能。「新しい管理配信経路が認証付き」と「そのファイルの全経路が認証必須」を区別する。前者を今回の到達点とし、後者を達成済みとは報告しない。
- 完全非公開が必要な対象の旧経路遮断・保存方法変更・移行は、公開側の利用を特定した後に別段階で設計する。既存ファイルの移動・token無効化・公開用途の再登録を今回の前提にしない。

この方式は公開側の画像切れを避けながら管理側を段階強化できる。ログアウト後に新しい管理URLから取得できないこと、公開側の既存URLは引き続き表示できることの両方を検証する。

## 現状と対象

- `Templates/__item_edit.tpl`、`__item_viewer.tpl`、`__item_viewer_notag.tpl` が画像・ファイルを表示する。画像は `__image_preview.tpl` と既存の拡大ビューアー、ファイルは `download-link` を使う。

## 提案する構成

### 1. 標準添付の識別と認可を共通化

新しい配信処理はノート・レコード・項目・元画像/サムネイル・取得方式を受け取り、サーバー側でファイルIDと保存先を解決する。入力されたパスやファイルIDだけでは許可しない。IDや署名は対象の識別であって、権限の代わりにしない。

判定順序は、有効な管理ログイン → ノートの閲覧許可 → 対象レコード・項目の読取り許可 → 現在もその項目がそのファイルを参照していること → 実体の存在、の順を基本とする。削除・差替え後の古いURLは拒否する。子ノートは必要な親の閲覧条件も適用する。

標準画面と配信で共有する「読取り認可」の処理を設ける。既存visibility_filterの関数名許可リストへ新しい配信関数を無条件に通すだけの実装にはしない。既存のノート権限とDSPの行・項目制限を保ち、アプリ固有の親子・公開条件はアプリ側の明示した判定に接続する。単なる検索条件・担当者絞込みは権限条件に読み替えない。DSPだけでも未定義対象は拒否されないため、DSPを認証やノート権限の代用にしない。

共通ヘルパーから認証付きURL/ダウンロード属性を生成し、上記標準テンプレートへ渡す。既存のアプリ専用配信を使う場合も、所属と認可を共通処理へ接続する。`get_file_info()` の既存返却形式を一括変更して全アプリを破壊しない。具体的なAPI名・設定項目名は実装前に確定する。

### 2. ファイルの配信区分をサーバー側で管理

配信区分は「管理認証付き」「明示した公開」「移行中の未分類」を区別する。標準ノートの新規添付は強化を有効にしたアプリで管理認証付きを既定とする。公開クラスから呼ばれたことや公開URLを作ったことだけで、管理用のファイルを公開へ変換しない。

既存の所属情報を使い、項目と現在の参照を照合する。複数レコードで共有しているファイル、所属不明、削除済みレコード、生成ファイル、固定フォーマットDBは自動で公開/非公開を決めない。必要な対応関係と経路を整理してから移行する。公開利用は公開状態・期限・対象範囲をサーバー側で登録・確認する。公開/非公開の共用は別ファイルに分けることを基本とし、曖昧な場合は管理用の保護を優先する。

公開会員・LINE・署名付きAPI・MCPなど、管理セッション以外の正当な認証経路も区別する。管理ログインがないという理由だけで既存の認証済み連携を一律に禁止せず、各入口の検証済み主体と対象範囲を使う。公開入口に管理認証を必須化して済ませない。

### 3. 同じ実体を返す経路も保護

管理認証付きの保存実体には、旧 `db_exe` URL、`upload/pull`、`public_media` のtokenを渡しても、未認証・権限なしでは返さない。元画像・サムネイル・ダウンロード・inline・HEAD/Rangeなど採用経路で同じ判定を通す。

ファイル配信の共通ガードに配信区分と認可を集約し、フレームワークの配信入口に適用する。`public_media` や `upload/pull` の直接readfileも対象とし、低レベルの画像・ファイル・メディア応答を呼ぶ別経路から抜けない構成を実装時に確認する。旧pathからも保護区分を逆引きできることが必要。逆引き失敗時に保護対象を公開扱いへ戻さない。DB依存はFFMの規則に従って事前に開き、再帰的な認証・DSP呼出しを避ける。

旧URLでも正当にログイン済みで対応レコードを一意に確認できれば継続利用を検討できるが、不明・曖昧・権限なしなら拒否する。ログインなしの旧URL互換を残して保護完了とはしない。

アプリの独自readfile、静的URL、別ストレージ、CDNや生成サムネイルは個別棚卸しが必要。フレームワークのガードだけで任意のPHPによる読出しまで防げるとは扱わない。過去に取得・保存されたファイルやブラウザーキャッシュを後から回収することもできない。

### 4. 非公開応答のキャッシュ

非公開応答は `private, no-store` を基本とし、共有キャッシュや公開CDNへ載せない。公開画像のキャッシュは維持する。表示の遅延やちらつきは見た目に影響するため、画像の多い一覧で確認し、失効を無視したキャッシュ延長では解決しない。ストリーミング開始前に認可し、範囲要求や再要求でも判定する。

## 既存システムに影響しやすい用途

| 用途 | 想定される影響 | 移行時の扱い |
| --- | --- | --- |
| 通常の管理画面 | 正常ログイン中は外観を維持可能 | 同じデータ・画面幅で比較 |
| 管理添付URLを他人へ共有 | 未ログインで開けなくなる | 意図した保護。公開共有要件があれば別に設計 |
| メール・LINEの画像やリンク | 管理セッションがなく表示できなくなる可能性 | 本来の公開配信/認証済み会員配信へ分類して移行 |
| 公開ページの画像・資料 | 誤分類すると画像切れ・取得不能 | 公開用途を確認し公開のまま維持 |
| PDF等のサーバー側画像読込み | セッションなしHTTP取得が失敗する可能性 | 認可済み内部解決を設計。全体の公開解除で逃げない |
| アプリ独自テンプレート・JS | 古いdata属性やURL指定が残る | 共通生成処理への接続と取得経路を確認 |
| 一覧の大量サムネイル | 権限照合・再取得で遅延する可能性 | リクエスト内の安全な再利用・索引を検討し測定 |

既存アプリ全件の用途・外観を調査済みではない。上表はソース上の経路から予測する影響であり、本番互換性の保証ではない。

## 段階導入

1. 共通機能を追加しても既存アプリの配信区分を自動で一括変更しない。未分類を互換運用するアプリは、保護未完了として記録する。
2. app-fwtestで管理添付・公開素材・各取得経路を検証し、app-one2oneを最初の移行対象とする。既存の認証付き配信を再利用し、標準入力への接続を確認する。
3. app-one2oneの既存添付・顔写真を所属/公開用途まで分類し、旧tokenを含む拒否試験が通ってから強化を有効にする。新規だけ保護して既存も保護済みとはしない。
4. 他アプリは用途別に棚卸し・テストして移行する。移行済みの保護対象は他の公開入口からも保護する。
5. 切戻しはまず旧UIから認証付き取得先を呼ぶ形を検討する。取得不能を直すため全ファイルを無認証へ戻す操作は、通常の切戻しに含めない。

## 実装後の判定基準

- 同一データ・同一画面幅で、一覧・子一覧・詳細・登録・編集・削除確認、画像拡大のスクリーンショットと主要要素の寸法・配置を比較する。画像の多い画面の読込みも確認する。
- ファイル名、日本語名、画像形式、元画像/サムネイル、既存ファイルの取得、差替え後の表示、公開画像が従来どおりであることを確認する。
- 許可ユーザーの正常取得に加え、未ログイン・失効・権限なし・別レコード/別項目への改ざん・削除/差替え済み・親閲覧不可を拒否する。共有設計では別担当の正当なチーム利用者を拒否しない。
- 同じ実体に対して旧URL・旧token・`upload/pull`・`public_media`・サムネイル経路を確認し、本文が漏れないことを実HTTPで検証する。エラー画面への遷移だけで成功扱いにしない。
- 公開配信、既存の認証済み連携、独自テンプレート、キャッシュヘッダ、ダウンロードのエラー表示を確認する。

現時点の結論: 正常な管理画面の見た目を変えずに強化する設計は可能。ただし、ログインなしで管理用URLを使う既存用途は動作が変わる。実装・代表画面比較・アプリ別の用途確認を終えるまでは「全システムで見た目が変わらない」とは断言しない。
