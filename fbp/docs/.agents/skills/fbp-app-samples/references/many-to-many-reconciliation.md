# 多対多突合＋通帳CSV サンプル

計上明細と実際の銀行入出金を多対多で紐付ける、管理者向けの独立した業務サンプル。
金額不一致でも対応関係を先に保存し、差額を双方の一覧で確認する。
顧客固有の保証会社名・賃料計算・本番データに依存しない。

## 含めるもの

- 計上と入出金のStandard Screen、双方の「突合」「突合解除」「グループ詳細」。
- 既存の関係を保持する追加、複数選択、直接関係1本ずつの解除。
- 連結した全体の計上合計・入金合計・差額を両側の一覧に表示。
- 日付降順・ID降順、キーワード／日付／紐付け状態検索、100件単位のページング。
- 選択後に合流する既存グループも含めた合計プレビュー。
- 関係と金額一致の分離、操作履歴、古い画面の保存拒否、重複防止。
- 通帳CSVアップロード→プレビュー→取り込み、元ファイル／行／銀行取引IDの追跡。
- 出金行の保持と対象外化、利息の対象外化を選べる取込設定。

初期版はJPYの整数金額・アプリ管理者専用。管理者はサンプルの全管理範囲を閲覧できる。
`scope_key`は結合を分けるキーであり、ユーザーごとの閲覧認可の代用品ではない。
他の通貨、取引先別の閲覧権限、個別充当額、返金、仕訳、承認、自動突合は含めない。
特に自動突合を追加する際も、関係の根拠と金額一致を別に判断し、同じ保存サービスを使う。

## DB・計算の正本

[many-to-many-reconciliation-db.md](many-to-many-reconciliation-db.md)と
`assets/many-to-many-reconciliation/many-to-many-reconciliation.json`を参照。
コードを既存案件へ適用する場合は左右の明細取得をアダプター化する。
既存業務の金額を別テーブルへ複写して二重管理しない。

コード配置とテスト定義登録は別操作。インストーラーはデータを投入しない。
同名クラス／ノート／選択肢を上書きしない。途中失敗時は成功済み定義を確認して復旧する。
本番への導入・移行・リリースはこの操作に含まれない。

## 通帳CSV

先頭行に列名を置く。UTF-8（BOM可）／Shift_JIS、2MB、5000行まで。

```csv
入出金日,摘要,入金額,出金額,残高,取引ID
2026/11/01,架空入金A,40000,0,40000,example-001
2026/11/02,架空入金B,32000,0,72000,example-002
2026/11/03,架空出金,0,1000,71000,example-003
```

架空の確認用CSVは`assets/many-to-many-reconciliation/examples/bank-statement.csv`に同梱する。自動投入はしない。

日付はYYYY/MM/DDまたはYYYY-MM-DD。金額は円単位の非負整数、残高のみ負数も可。
カンマを含む金額はCSVの通常の引用符で囲む。入金・出金の同時入力はエラー。
入出金がともに0の行は取り込まない。

画面で管理範囲と口座識別子を指定する。同じ銀行口座には毎回同じ識別子を使う。
入金額は突合の金額、出金額・残高は通帳の原情報として保持する。
出金行は対象外にし、「利息」の対象外化は画面のチェックで選ぶ。
取り込みは既存明細の金額や紐付けを更新しない。

### 重複と日付・列の差

- 銀行取引IDがあれば管理範囲＋口座＋取引IDで識別する。同じIDの内容違いは停止する。
- IDなしの場合は論理的なファイル内容＋行位置で同一ファイルの再取り込みを防ぐ。
- IDなしの別ファイルで既存と同じ日付・摘要・入出金額・残高の行があれば、
  同一とも別取引とも推測せず取り込みを停止する。銀行の安定した取引IDをアダプターで取得する。
- 正当な同日同額取引を黙って削除しない。同じ取引を二重登録するための偽のIDも作らない。
- 銀行固有のヘッダ前置き・和暦・独自列・単一金額＋取引区分の形式は、`Parser.php`へ
  独立した変換ルールと試験を追加してから使う。任意の銀行CSVをそのまま読めるとは扱わない。

確認後にもう一度重複を検査する。複数行の取込はFFMの全行トランザクションではないが、
途中失敗後の同じプレビューの再送では保存済みのsource_keyを飛ばして続行できる。

## 操作・表示

計上72,000円に入金40,000円を追加すると不足32,000円。
続けて32,000円を追加すると一致。両入金の一覧でも計上72,000円・入金72,000円・差額0円を表示する。
さらに別の計上を結ぶと、その計上を含むグループ全体へ合流する。

差額は常に「入金合計−計上合計」。自身の金額とグループ合計を区別する。
グループ合計を行数分足し直さない。初期サンプルでは一覧の総合計行を付けない。
検索範囲外の関連明細もグループ合計に含まれる。
未紐付け0円を「一致」「完了」と表示しない。グループの一致は個々の完済とは別。

追加は成功後に閉じる。解除は成功後に同じダイアログを更新し、続けて解除できる。
入力エラーではダイアログや選択を作り直さない。
直接関係のない間接的な明細には解除ボタンを表示しない。
履歴のある元明細は物理削除を拒否する。解除後に対象外へ変更して保持する。

## 実装構造・排他

- `Graph.php`：純粋な連結範囲・合計・金額検証。
- `Store.php`：FFMの事前オープン、最新値再読込、関係の追加／解除、履歴復旧、一覧派生値。
- `sample_reconciliation.php`：管理者認可、セッション付き画面トークン、検索・ページング・保存。
- `Guard.php`：管理ノートの認可、派生項目・取込識別子への不正POST、関係がある明細の削除等を拒否。
- `sample_statement_csv`：アップロード検証・銀行CSV変換・取込前後の重複検査。

一覧の合計欄は再生成可能なキャッシュ。追加・解除・CSV取込・元明細の保存後処理で更新する。
標準一覧はread-onlyのため表示時のDB更新は行わない。外部取込も同じ保存サービスを経由し、
直接DBを変更した場合は専用の派生値更新処理を呼ぶ。元金額を自動訂正しない。
データ量が大きい案件では、影響グループ限定の計算・キャッシュ無効化へ適応する。
初期版の古い画面判定はサンプル全体の指紋であり、別グループの変更でも再表示を求める。

独自flockは使わず、全4DBを開いてから判定に使うデータを読む。
履歴の書込待ち情報を関係の同じ行に保存し、履歴保存失敗後は次の操作前に復旧する。
関係ID＋revisionをイベントキーにして履歴を二重作成しない。
FFMのクラッシュ時のファイル破損まで保証するものではない。
複数関係の一括追加は1関係ずつ記録するため、途中失敗では一部が保存され得る。
再表示して未追加分を追加でき、既存関係を上書き・重複させない。

SQLへ移す場合は関係ペアとイベントキーの一意制約・外部キーをDBでも保証し、
関係とイベントを同一トランザクションにまとめる。

## 検証

```sh
php "$SKILL_ROOT/scripts/test_many_to_many_reconciliation.php" \
  --temp-root="$EMPTY_SCRATCH_ROOT" --framework-root="$FRAMEWORK_FBP_ROOT"
```

manifest／PHP構文、隔離インストール・上書き拒否、関係計算、保存・解除、権限、
古い画面、履歴復旧、CSVの符号化・重複・類似明細、実FFMの別プロセス同時実行を検証する。

実環境はテスト用アプリに導入し、各ノートの`standard_screen_check`を行う。
内部2ノートの手動追加・編集・削除画面なしは意図した警告。
画面操作は`scripts/verify_many_to_many_reconciliation.cjs`をPlaywright環境で使う。
明示したテストURL・実行rootとログイン情報を環境変数で渡す。既存workflowサンプルと同じ
`APP_TEST_URL`、`APP_LOGIN_ID`、`APP_PASSWORD`、`SAMPLE_TEST_ROOT`、`SAMPLE_TEST_OUTPUT_DIR`を使う。
ゲートウェイ認証とブラウザ実行ファイルは起動環境から指定する。
架空明細を生成し、今回生成した明細・関係・履歴だけをfinallyで削除する。
