# PDF Delivery

PDFの基本方式は Controllerの `show_pdf()` による画面内表示。オブジェクトで組み立てた帳票の直接取得は `$pdf->download_pdf()` を使う。tpl方式の直接取得は従来の `save_pdf()` + `res_saved_file()` も利用できる。

| 入口 | 呼び出し先 | 応答 |
| --- | --- | --- |
| `ajax-link` の「請求書を表示」 | `preview()` → `show_pdf()` | ダイアログJSON。その後 `apppdf.php` がPDFを返す |
| 通常リンクの「請求書を直接ダウンロード」 | `download()` → `$pdf->download_pdf()` | PDF本体（内部で `res_saved_file()` を使用） |

`download-link` や通常リンクから `show_pdf()` を直接呼ばない。逆にPDF本体を返す関数を `ajax-link` から呼ばない。公開PDFの直接取得はLINE利用の有無によらずGETリンクを標準とする。管理画面などPOSTが必要な場合は `fbp-pdf` に従って `download-link` を使い、理由を記録する。

## Install

`assets/pdf-delivery/` の公開 `page` / `preview` / `download` は固定の架空データのみ。DB定義・外部サービス・認証情報は不要。私有帳票には下記の `protected_page` / `protected_download` を使う。

編集元のクリーンなアプリに `php scripts/install_pdf_delivery.php <app-root>` で配置する。既存 `public_pages` は上書きしない。環境の同期手順で実行環境に反映し、`public_pages/page` を開く。

## 必須の適用単位

説明だけでなく `assets/pdf-delivery/public_pages/public_pages.php`、採用方式のテンプレート、検証スクリプトを読み、該当部分をコピー・適応する。公開直接取得はGETリンク → PDF本体、表示はAjax → ダイアログ → PDFの組を維持する。tplなし帳票は生成オブジェクトの `download_pdf()` を呼び、出力バッファ・保存・削除処理をアプリへコピーしない。認証と正常/異常応答の契約は維持する。

## 認証付き帳票

`protected_page.tpl` → `protected_download()` を使う。`pdf_delivery_access.php` はセッション内に画面ごとのランダムな取得コードと本人・帳票・期限を保持する。共通フォームのCSRFや「最後に開いた帳票」を認証情報として使わない。別画面の表示で既存コードを上書きせず、15分以内・最大64件の範囲で複数タブを維持する。64件を超えると古いリンクは拒否される。再表示で新コードを発行する。コードだけを別セッションへ持ち出しても取得できない。

必ず実装するフック:

- `authenticated_subject()`: サーバー側で検証済みの利用者IDを返す。未認証・無効会員なら `null`。リクエストの利用者IDをそのまま採用しない。ログアウト時は本人情報と `pdf_delivery_grants` を消す。
- `load_document($ctl, $id)`: `$id === null` は本人確認済み入口から選んだ帳票、非nullはそのIDの帳票をDBから毎回読み直す。`id`、`owner`（本人ID）、`issuable`（真偽値）、`issued_at`（時刻）、`amount` を返す。キャンセル・未入金等の発行条件はここで判定する。不存在・不許可なら `null`。本文テンプレートも実際の宛名・件名等へ適応する。

フック未実装では403案内となる。公開デモの固定データや無条件認証で穴埋めしない。確認メールが本人確認の入口なら、署名/暗号化コードとDBの有効性を検証してから本人文脈を確立する。選択中の申込IDと本人IDを混同しない。複数のメール確認を許すアプリでは、確認済み対象を対象別に保持・再検証するフックにし、単一の最新申込みで過去の確認状態を上書きしない。

取得時も、コード・セッション・現在の本人・対象ID・現在の所有者・発行可否を照合してからPDFを生成する。GETは閲覧/取得に限定し、入金確定等の業務更新を行わない。拒否は403の `document_error.tpl` とし、通常のブラウザー遷移へ通知JSONを返さない。私有帳票と入口は `private, no-store`、`no-referrer` を付け、取得コードを証票や通常ログへ記録しない。成功応答のヘッダーと管理ファイルの削除は `download_pdf()` が担当する。

このサンプルの認証付き方式は直接ダウンロード用。認証付きプレビューが必要なら `apppdf.php` 側の権限・失効も確認し、公開固定サンプルの `preview()` をそのまま流用しない。

## Verify

- PHP lint、manifest解析、空の一時配置先へのインストールと既存ファイル上書き拒否を確認する。
- `php scripts/test_pdf_delivery.php` で認証付き経路の拒否・再検証・複数画面保持を確認する。これはモックによる契約テストであり、実ブラウザー検証の代替ではない。保存・削除はフレームワークの `tests/pdfmaker_output_test.php` が実PDF生成、例外、並行取得、exit後の削除を検証する。
- 実行環境のCLIで `public_pages/page` と `public_pages/preview` を呼び、後者がダイアログを返すことを確認する。これはPDF取得完了の検証ではない。
- `scripts/verify_pdf_delivery.cjs` をPlaywright環境で実行する。`PDF_SAMPLE_URL` にサンプルページのURL、`PDF_TEST_OUTPUT_DIR` に生成物の保存先を渡す。既存アプリで認証が必要なら `PDF_STORAGE_STATE` を指定する。
- 実ボタンをクリックし、プレビュー後のPDF応答と直接ダウンロードをそれぞれ確認する。HTTP成功だけでは不十分。`application/pdf`、`%PDF-`、PDF解析、金額・件名・発行元を確認する。
- PCとスマートフォンで検証する。スマートフォンの `show_pdf()` はダイアログ内の保存リンクを押して取得する。
- 顧客アプリに適用するときは、セッション切れ・非公開・権限不一致でPDFを返さず案内になることも確認する。固定公開サンプルにはセッション認証を持ち込まない。

認証付き経路のブラウザー検証では `PDF_PROTECTED_URL` を本人確認済みの帳票画面に設定する（必要なら `PDF_STORAGE_STATE` を使用）。同じ画面を別タブで再表示した後に元タブから取得、リンクの再取得、不正コード、別セッションを検証する。アプリの本人確認入口からその画面までの操作、別帳票を開いた後の元帳票の宛名/番号一致、期限切れ、ログアウト、所有者・発行可否変更も対象アプリのfixtureで確認する。テストで本番データを変更しない。

Chromiumの幅390pxはSafari・LINE実機の確認を意味しない。申告ブラウザーと入口が異なる、または失敗条件を再現できない場合は「修正完了」にせず、検証済み範囲と不足条件を記録する。障害の修正では変更前の失敗→同じ条件で変更後の成功を証票にする。

PDF解析には `pdftotext` を使用。LINEアプリ固有の保存挙動はPlaywrightによるスマートフォン模擬だけでは保証しない。
