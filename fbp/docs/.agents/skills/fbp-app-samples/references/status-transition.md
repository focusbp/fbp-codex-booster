# 状態変更と確認ダイアログ

案件を標準画面で登録し、行の「状態を変更」から理由を入力して進める。`0:未対応 → 1:対応中 → 2:完了` の一方向のみ。状態のラベルは `constant_array` から取得する。

状態・履歴・versionは通常の編集項目にせず、visibility filterでも直接POSTによる書換えを拒否する。`sample_cases_post_action` は追加直後の空状態のみを初期化し、既存案件をリセットしない。状態変更の確認内容はセッションに保存し、送信された対象ID・状態を信用しない。

保存時にversionと状態を再確認し、状態と履歴を同じレコードで更新する。FFMのロックを取得から更新まで保持する。成功時に確認トークンを消費し、再送で履歴を増やさない。失効・競合時は一覧から開き直す。変更理由は300文字以内、履歴は6000bytes以内。

差し戻し、再開、多段承認、通知は含まない。履歴は業務上の記録であり、管理者によるレコード削除も禁止する監査ログではない。

## 導入

[共通手順](workflow-samples.md)に従い、`status-transition` を指定する。コードと設定の正本は `assets/status-transition/`。構造は [status-transition-db.md](status-transition-db.md) を参照。

## 確認する操作

- 標準画面で新規案件を作り、初期状態「未対応」を確認する。
- 理由未入力はダイアログ内にエラーを表示し、入力内容を保持する。
- 2回の変更で「完了」になり、理由・日時・操作ユーザーIDが2件残る。
- 二重送信、古いversion、失効トークン、非管理者、通常編集からの状態改ざんを拒否する。
